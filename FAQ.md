# Частые вопросы о VoiceBot

За время работы проекта мне задавали много вопросов — от архитектуры до деталей реализации. Собрал тут самые частые здесь, чтобы не повторяться на каждом собеседовании.

---

## Q: Почему Asterisk, а не Twilio или Voximplant?

**A:** Три причины:

**Экономика.** VPS стоит ~1000₽/мес, звонки идут по SIP без абонентской платы. Twilio/Voximplant — плата за минуту, для малого бизнеса это делает автоматизацию нерентабельной.

**Контроль.** Voximplant — готовый продукт-чёрный ящик: когда бот начинает озвучивать эмодзи или галлюцинировать, ты не можешь влезть внутрь. С Asterisk я управляю вызовом программно через ARI и Stasis — каждая стадия (запись, VAD, playback, hangup) под моим контролем. Пример: проблему «бот читает звёздочки» я закрыл своим clean_for_tts, в облаке это было бы невозможно.

**Приватность и независимость.** Голоса клиентов не уходят на чужие сервера — закрытый контур. Плюс нет vendor lock-in: open source не поднимет цены и не закроет API.

**Trade-off:** Asterisk сложнее в администрировании — pjsip, dialplan, RTP-порты настраиваю сам. Но я осознанно плачу временем за ноль рублей и полный контроль.

## Q: Почему aiohttp, а не FastAPI или Flask?

**A:** Выбор обусловлен характером нагрузки:

**aiohttp/asyncio** — асинхронный фреймворк, идеален для I/O-bound задач. Каждый звонок = корутина, event loop переключается между ними пока ждём ответа от внешних API (Groq, ModelScope). Потоки не нужны — нет оверхеда на контекстные переключения.

**FastAPI** — отличный фреймворк, но он оптимизирован под HTTP-запросы с быстрым ответом. Мой бот держит WebSocket-соединение с Asterisk на весь звонок (это может быть 2-5 минут), плюс стримит аудио. aiohttp лучше подходит для long-lived connections.

**Flask** — синхронный, для одновременных звонков нужны были бы потоки или процессы. На VPS 2CPU это быстрее упрётся в ресурсы.

**Результат:** на одном event loop держу 2-3 одновременных звонка без потоков.

## Q: Почему Docker для Edge-TTS, а не системный пакет?

**A:** Две причины:

**Изоляция версий.** Edge-TTS — сторонняя библиотека, Microsoft может поменять API. В Docker я фиксирую версию, и она не сломается при обновлении системы. Если что-то пойдёт не так — откатываюсь на предыдущий образ.

**Независимое масштабирование.** TTS живёт в отдельном контейнере на порту 8201. Если нужно больше производительности — могу запустить N контейнеров TTS и балансировать нагрузку между ними, не трогая основной бот.

**Trade-off:** Docker добавляет оверхед (~100-200 МБ RAM), но даёт предсказуемость и масштабируемость.

## Q: Почему systemd, а не Kubernetes?

**A:** Один VPS, один разработчик — Kubernetes это overkill.

**systemd** — система инициализации в Linux. Мой бот работает как systemd-сервис: автозапуск при загрузке, автоматический рестарт при crash, логи через journalctl. Простая конфигурация, стандартные команды.

**Kubernetes** — оркестратор контейнеров для распределённых систем. Нужен кластер из нескольких нод, это дорого и сложно для одного VPS. Плюс K8s требует глубоких знаний — настраивать pods, services, ingress, это отдельная работа.

**Когда перейду на K8s:**
- Когда нагрузка вырастет до 10+ одновременных звонков
- Когда будет несколько VPS для балансировки
- Когда появится команда DevOps для поддержки

Сейчас systemd покрывает все потребности: автозапуск, рестарт, логи.

## Q: Как вы мерили latency в 2.5 секунды?

**A:** Декомпозиция по шагам с таймстампами:

**Бюджет latency:**
- VAD-ожидание тишины: ~1с (порог детектора)
- Groq Whisper STT: 0.3-0.5с (API response)
- Qwen3-30B генерация: 0.7-1.8с (зависит от длины контекста)
- Edge-TTS синтез: ~0.5с
- **Итого:** ~2.5с в среднем

**Хвост до 5-7с:** длинный контекст диалога → дольше prefill у модели + длиннее генерация.

**Как мерил:** каждый шаг пишу в JSON-лог с таймстампом (это же кормит voicebot-analytics). Вижу p50/p95 по каждому этапу.

**Что можно оптимизировать:**
- Стриминг TTS: озвучивать первое предложение, не дожидаясь полной генерации
- Ограничение контекста: держать последние N реплик в промпте, а не всю историю
- Переезд LLM на Groq: там LPU, инференс быстрее

**Qwen3-30B уже в non-thinking режиме** — модель не тратит токены на внутренние рассуждения, это осознанно экономит latency.

## Q: Что если одновременно позвонят два человека?

**A:** Держатся по дизайну через async:

**Один event loop, каждый звонок — корутина.** Пока первый ждёт Groq по сети (I/O), loop обслуживает второй. Потоки не нужны — нет оверхеда на контекстные переключения.

**Реальных узких места два:**
1. **CPU:** VAD и обработка аудио — CPU-bound операции, блокируют event loop. На VPS 2CPU честно 2-3 звонка, не больше.
2. **Free-tier лимиты:** два параллельных запроса к Groq могут упереться в RPM. На этот случай у бота свой rate limiting.

**Graceful degradation:** если второй звонок словил лимит (429), бот говорит «сейчас я занят, перезвоните», а не тишину. Абонент понимает что произошло.

**Масштабирование:**
- Платный API с высокими лимитами
- Локальная модель через Ollama/vLLM без внешних лимитов
- Разнесение TTS в отдельный контейнер (уже сделано)

## Q: Чем отличается is_hallucination от is_bad_answer?

**A:** Разные слои защиты, каждый ловит свой класс мусора:

**is_hallucination** — стоит ПОСЛЕ Groq, до LLM. Отсекает известные галлюцинации Whisper на тишине (типа «Субтитры сделал DimaTorzok»). Если тишина была, а Whisper что-то услышал — это галлюцинация, бот не отправляет её в LLM.

**is_bad_answer** — стоит ПОСЛЕ LLM, до TTS. Бракует мусорные ответы самой модели: если LLM вернула `http`, `error`, `<html>`, `traceback` или прочий служебный мусор — бот не озвучивает это, а говорит «не расслышала, повторите».

**clean_for_tts** — стоит ПОСЛЕ is_bad_answer, перед TTS. Срезает markdown (`**bold**`, `# headings`, списки), чтобы TTS не читал «звёздочка-звёздочка».

**Защита в глубину:** каждый слой ловит свой класс мусора, если один пропустит — следующий поймает.

## Q: Сколько стоит один звонок?

**A:** ~$0.001 за звонок на free-tier API:

- **Groq Whisper:** ~$0.0003 за транскрипцию (free tier)
- **Qwen3-30B через ModelScope:** ~$0.0005 за генерацию ответа (free tier)
- **Edge-TTS:** бесплатно (Microsoft voices)
- **VPS:** ~1000₽/мес = ~$11/мес, делим на количество звонков

**Итого:** при 1000 звонков в месяц стоимость ~$1 за все звонки + $11 за VPS.

**Если перейду на платные API** (OpenAI Whisper + GPT-4): стоимость вырастет до ~$0.05-0.10 за звонок, но latency улучшится и лимиты исчезнут.

## Q: Что если Groq API упадёт?

**A:** Три механизма:

**1. Rate limiting.** Бот сам считает запросы к Groq и не превышает free-tier лимиты (RPM/TPM). Если приближается к лимиту — замедляет обработку.

**2. Graceful degradation.** Если Groq вернул 429 (Too Many Requests) или 503 (Service Unavailable), бот не молчит и не crash'ит. Он говорит вежливую фразу: «Сейчас я занят, перезвоните позже» и завершает звонок. Абонент понимает что произошло, а не слышит тишину.

**3. Fallback (в roadmap).** Можно добавить OpenAI Whisper как backup-провайдер: если Groq недоступен, переключаемся на OpenAI (дороже, но работает).

**Важно:** graceful degradation — это не «система упала», это «система работает в ограниченном режиме». Абонент получает честный ответ, а не баг.

## Q: Как бот понимает, что абонент договорил?

**A:** Через VAD (Voice Activity Detection). ARI record пишет аудио в стрим, VAD смотрит амплитуду фреймов: тишина ниже порога держится ~1 секунду — значит абонент договорил, запись закрывается и улетает в Groq на распознавание.

Плюс есть ограничитель максимальной длины реплики — чтобы бот не слушал вечно, если абонент замолчал и не кладёт трубку.

**Trade-off:** порог тишины слишком короткий — обрежу абонента, который сделал паузу подумать; слишком длинный — лишняя задержка в цикле. Я балансировал около секунды.

**Бонус:** Whisper large-v3 обучен на шумных данных, поэтому ветер/шум улицы не превращается в мусорный текст — это шумоустойчивость модели, не VAD.

## Q: Почему Qwen3-30B, а не GPT-4 или Claude?

**A:** Три причины:

**1. Стоимость.** GPT-4 и Claude — платные API ($3-15 за миллион токенов). Qwen3-30B через ModelScope — бесплатный free tier. Для pre-production тестирования это критично: я делаю сотни звонков, платный API разорит.

**2. Размер модели.** 30B параметров — это баланс между качеством и скоростью. 70B+ модели медленнее (больше latency), 7B — слабее держат контекст. 30B — sweet spot.

**3. Non-thinking режим.** У Qwen3 отключён thinking-режим — модель не тратит токены на внутренние рассуждения, это экономит latency и стоимость.

**Trade-off:** ModelScope медленнее OpenAI (latency 0.7-1.8с vs 0.3-0.5с у OpenAI). Но бесплатно.

**В roadmap:** переезд LLM на Groq (там LPU, инференс быстрее) или локальная модель через vLLM.

## Q: Как добавить новый домен (например, стоматологию)?

**A:** Config-driven подход: новый домен = новый YAML-файл, код не трогаем.

**Шаги:**
1. Создать `configs/dentistry.yaml` с:
   - System prompt (роль: стоматолог-консультант)
   - Примеры диалогов (few-shot)
   - Список услуг (чистка, пломбы, импланты)
   - Фразы для записи на приём

2. В `bot.py` указать какой конфиг использовать (или добавить роутинг по номеру телефона)

3. Перезапустить бот: `systemctl restart voicebot`

**Результат:** бот теперь стоматолог-консультант, знает про услуги, записывает на приём. Код не менялся.

**Почему так:** бизнес-правила меняются часто (новые услуги, акции), код — редко. Разделение = меньше багов, быстрее изменения.

## Q: Где я могу посмотреть живое демо?

**A:** Сейчас система работает в тестовом режиме: я звоню через Linphone (SIP-клиент) на локальный Asterisk, бот отвечает.

**Для production** нужен SIP-провайдер (Задарма, Манго, Телфин) + арендованный DID-номер (~500-1500₽/мес). Тогда обычные люди смогут звонить на городской номер, звонок придёт в мой Asterisk через SIP-транк, и бот будет отвечать как полноценный колл-центр.

**Почему ещё не в production:**
- Для демонстрации достаточно тестовой среды
- Production требует аренды номера и настройки SIP-транка (это 1-2 часа работы, но стоит денег)
- Планирую запуск после первого коммерческого проекта

**Как протестировать локально:**
1. Клонируй репозиторий
2. Подними Asterisk + edge-tts + бот по README
3. Установи Linphone (или любой SIP-клиент)
4. Зарегистрируйся в Asterisk (sip.conf)
5. Звони на внутренний номер 200 — бот ответит

## Q: Как вы тестировали систему?

**A:** Два уровня:

**1. Юнит-тесты (pytest).** Покрывают критичные функции:
- `clean_for_tts` — проверяет что markdown срезается правильно
- Защиты (is_hallucination, is_bad_answer) — проверяют что мусор отсекается
- CI на GitHub Actions прогоняет тесты на каждый push

**2. Production-тестирование.** Система работает 24/7, принимает реальные звонки. Логи диалогов пишутся в JSON → кормят voicebot-analytics → я вижу конверсию, слабые точки, причины завершений. Это лучше любых синтетических тестов показывает что система работает.

**Чего НЕТ:**
- Юнит-тестов на весь пайплайн звонка (слишком сложно мокать Asterisk + ARI + внешние API)
- Нагрузочного тестирования (нагрузка ограничена телефонным трафиком одного номера)

**Trade-off:** осознанно не покрываю тестами всё, фокус на критичных частях + production-метрики.
